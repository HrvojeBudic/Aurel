# P1.4.14 — Operator Consent Binding

## 1. Summary

P1.4.14 adds Operator Consent Binding to Aurel's identity layer. Building directly on P1.4.13's Authority Delta Detector, this patch enables Aurel to formally bind Operator consent to specific authority deltas with exact attestation-level precision.

Consent is **not** global, **not** permanent by default, **not** transferable, and **not** capability verification. It is bound to exact delta IDs and attested source state pairs.

## 3. Scope

P1.4.14 implements:

- Operator consent request model (`OperatorConsentRequest`)
- Operator consent record model (`OperatorConsentRecord`)
- Consent binding validation (`ConsentBindingValidation`)
- Consent decision model (`OperatorConsentDecision`)
- Consent status enum (`OperatorConsentStatus`): REQUESTED, GRANTED, DENIED, REVOKED, EXPIRED, SUPERSEDED
- Consent scope enum (`OperatorConsentScope`): SINGLE_DELTA, DELTA_REPORT, SOURCE_UPDATE, SESSION_LIMITED
- `build_operator_consent_request()` — builds from `AuthorityDeltaReport`
- `grant_operator_consent()` — fails closed with risk acknowledgement requirement
- `deny_operator_consent()` — records denial
- `revoke_operator_consent()` — only works on GRANTED records
- `validate_operator_consent_binding()` — verifies status, attestation, delta, risk, scope, expiry
- CLI: `identity consent request|grant|deny|revoke|show|validate`
- JSON serialization for all models
- 55 tests (27 core + 14 seal + 10 CLI + 4 fixtures)

## 5. Implementation

### 5.1 Core module

**File**: `src/agentic_runtime/identity/operator_consent.py` (~600 lines)

Key design decisions:

- **Request ID determinism**: `request_id` is SHA-256 of (source_kind, sorted delta_ids, old_att_id, new_att_id) — same inputs produce same request ID.
- **Record ID determinism**: `consent_id` is SHA-256 of (request_id, operator_id).
- **Fail-closed grants**: `grant_operator_consent()` raises `ConsentValidationError` with blocker list when preconditions fail.
- **Risk acknowledgement**: HIGH/CRITICAL severity grants require `risk_acknowledged=True`. Validation checks this on record too.
- **Scope enforcement**: SINGLE_DELTA requires exactly one delta_id; DELTA_REPORT and SOURCE_UPDATE require all consent-required deltas covered; SESSION_LIMITED is unsupported (blocker: `scope_not_supported`).

### 5.2 Consent request model

```python
OperatorConsentRequest(
    request_id: str          # deterministic
    source_kind: str
    delta_ids: tuple[str,...] # only consent-required deltas
    highest_severity: str
    old_attestation_id: str|None
    new_attestation_id: str|None
    summary: str             # human-readable
    risk_summary: str        # risk-specific
    requested_scope: OperatorConsentScope
    requires_explicit_risk_acknowledgement: bool
    created_at: str
    expires_at: str|None
)
```

### 5.3 Consent record model

```python
OperatorConsentRecord(
    consent_id: str
    request_id: str
    status: OperatorConsentStatus
    scope: OperatorConsentScope
    operator_id: str
    operator_display_name: str|None
    source_kind: str
    delta_ids: tuple[str,...]
    old_attestation_id: str|None
    new_attestation_id: str|None
    highest_severity: str
    risk_acknowledged: bool
    granted_at/denied_at/revoked_at/expires_at: str|None
    reason: str|None
)
```

### 5.4 Consent binding validation

`ConsentBindingValidation` exposes:

- `valid: bool` — overall validity
- `blockers: tuple[str,...]` — why invalid
- `warnings: tuple[str,...]` — non-blocking concerns
- `covered_delta_ids / missing_delta_ids`

Blockers: `consent_not_granted`, `consent_revoked`, `consent_expired`, `consent_denied`, `source_kind_mismatch`, `old_attestation_mismatch`, `new_attestation_mismatch`, `delta_not_covered`, `risk_not_acknowledged`, `scope_not_supported`, `scope_violation`.

## 6. Consent scopes

| Scope | Coverage | Notes |
|-------|----------|-------|
| `SINGLE_DELTA` | Exactly one delta | Fails if report has additional consent-required deltas |
| `DELTA_REPORT` | All consent-required deltas in one report | Default |
| `SOURCE_UPDATE` | All consent-required deltas, attestation-bound | Same semantics as DELTA_REPORT, scoped to attestation pair |
| `SESSION_LIMITED` | Unsupported | Blocked with `scope_not_supported` |

## 7. Revocation / expiry

- **Revoke**: Only GRANTED records can be revoked (status → `REVOKED`, `revoked_at` set). Revoked records never validate.
- **Expiry**: Records with `expires_at < now` are invalid. `ConsentBindingValidation` checks expiry independently of status.
- **Denied**: Denied records are permanently invalid for binding validation.

## 8. Risk acknowledgement

For HIGH or CRITICAL authority deltas:

- `requires_explicit_risk_acknowledgement` = `True` in the request
- `grant_operator_consent()` rejects grants with `risk_acknowledged=False`
- `validate_operator_consent_binding()` rejects records with `risk_acknowledged=False` (blocker: `risk_not_acknowledged`)

## 9. CLI usage

```bash
# Build request from delta report
python -m agentic_runtime.cli identity consent request --delta-report report.json --json

# Grant consent (--ack-risk required for HIGH/CRITICAL)
python -m agentic_runtime.cli identity consent grant \
  --request request.json --operator-id op1 --ack-risk --json

# Deny
python -m agentic_runtime.cli identity consent deny --request request.json --operator-id op1 --json

# Revoke
python -m agentic_runtime.cli identity consent revoke --record record.json --operator-id op1 --json

# Show
python -m agentic_runtime.cli identity consent show --record record.json

# Validate
python -m agentic_runtime.cli identity consent validate --record record.json --delta-report report.json --json
```

## 14. Known limitations

- SESSION_LIMITED scope is unsupported (blocker: `scope_not_supported`). The runtime does not have a session model yet.
- SUPERSEDED status exists as an enum value but no `supersede_operator_consent()` function is implemented — can be added when multi-revision consent workflows emerge.
- No persistent storage — consent records exist only in memory. A future patch (P1.7+) should add disk persistence or a state DB layer.
- No notification channel — when consent expires or is revoked, Aurel cannot currently notify the Operator.
- Consent does not auto-expire on source change — the validation layer catches attestation mismatches, but consent records don't auto-invalidate on attestation churn.
