# P1.4.16 — Identity Test Battery

## 1. Summary

P1.4.16 implements an integrated, curated, adversarial test harness for the P1.4 identity/autonomy/governance stack. The battery tests the full chain — source attestation → authority delta → consent binding → CLI visibility — producing structured JSON-serializable reports and human-readable summaries. It does not add new authority, execute tools, grant consent, or mutate real config.

## 2. Preflight result for P1.4.15

P1.4.15 Identity Governance Command Surface is complete before implementation:
- `identity status` command exists
- `identity verify` command exists
- autonomy / claims / doctrine / attestation / authority-delta / consent command groups exist
- `IdentityCliStatus`, `IdentityCliEnvelope`, `IdentityStatusReport` exist
- JSON envelope stable
- Read-only guarantees for status/verify
- P1.4.15 report exists

## 3. Scope

- `IdentityBatteryStatus` (enum: PASSED/FAILED/DEGRADED/SKIPPED)
- `IdentityTestSeverity` (enum: INFO/LOW/MEDIUM/HIGH/CRITICAL)
- `IdentityTestCase` (frozen dataclass)
- `IdentityTestResult` (frozen dataclass)
- `IdentityTestBatteryReport` (frozen dataclass)
- Test case registry with 26 scenarios
- Scenario implementation runners for all cases
- CLI commands: `identity test-battery run`, `list`, `run-case`
- Human-readable battery summary format
- JSON serialization for all models
- Core tests (18 tests), integrated/seal tests (13 tests)

## 4. Non-goals

- No new autonomy/claim/doctrine/attestation rules
- No consent granting or tool execution
- No real source/config mutation
- No lifecycle identity states (P1.4.17)
- No full P20 seal
- Not a pytest replacement

## 5. Battery architecture

```
identity_test_battery.py          # Core engine: enums, dataclasses, registry, engine
identity_test_battery_scenarios.py # Scenario runner implementations (26 functions)
cli_modules/identity_commands.py  # CLI handlers (run, list, run-case)

```

### Data flow

```
IdentityTestCase → run_identity_test_case() → IdentityTestResult
                                                ↓
                                            run_identity_test_battery()
                                                ↓
                                        IdentityTestBatteryReport
                                                ↓
                            JSON serialization / human summary / CLI output
```

## 9. CLI test-battery command

```bash
# Run full battery
python -m agentic_runtime.cli identity test-battery run --json

# List cases
python -m agentic_runtime.cli identity test-battery list --json

# Run single case
python -m agentic_runtime.cli identity test-battery run-case --case-id consent_revoked_invalid --json
```

**CLI output (human):**
```
Identity Test Battery: PASSED

Total: 26
Passed: 26
Failed: 0

Next:
  identity verify --json
  identity test-battery list --json
```

**CLI output (JSON):** 26 case results, with status, severity, summary, errors, warnings, evidence_refs, and duration_ms per case.

## 10. Fixture strategy

- Dangerous cases use in-memory data and Python API calls — no file fixtures needed
- No real config or source mutation
- Temporary objects are scoped to function calls
- Battery default mode is read-only

## 11. Report format

All results are JSON-serializable. Report includes:
- `report_id` (hash-derived stable ID)
- `status` (PASSED/FAILED/DEGRADED/SKIPPED)
- `total_cases`, `passed`, `failed`, `degraded`, `skipped` counts
- `highest_failed_severity` (or null)
- `results` array with per-case detail
- `critical_failures` list
- `warnings` list
- `summary` text

## 14. Known limitations

- Duration tracking is coarse (function-boundary timing, not sub-ms)
- `duration_ms: 0` for immediate pass/fail results
- No progress bar or incremental reporting during battery run
- Scenario runners use late imports to avoid circular dependencies
