# P0.13 Tool Bus v1 Report

**Date:** 2026-06-17  
**Task:** P0.13 Tool Bus v1

## Summary

Implemented a minimal, stable Tool Bus v1 as the controlled execution surface
used by the Runtime. The Tool Bus registers tools, exposes structured metadata,
validates inputs when bound to `ToolContractRegistry`, executes handlers inside
the sandbox, and returns structured results/errors. It does not make policy,
authority, HITL, budget, verifier, trace, or memory-governance decisions.

## Tool Bus architecture

New stable concepts in `tools.py`:

- `ToolBus`
- `ToolRegistry`
- `ToolSpec`
- `ToolMetadata`
- `ToolExecutionContext`
- `ToolExecutionResult`
- `ToolError`
- `ToolSideEffectType`
- `ToolRiskLevel`
- `ToolSandboxRequirement`
- `ToolVerifierRequirement`

`ToolRuntime` now subclasses `ToolBus` and preserves the existing
`dispatch(CommandEnvelope) -> ObservationEnvelope` API used by `AgenticRuntime`.

## Security boundaries

- Filesystem paths flow through the sandbox, which rejects absolute host paths
  and traversal.
- Write tools cannot write outside the workspace root.
- Execution tools require timeout fields and execute through sandbox
  subprocess handling.
- Tool errors are structured (`ToolError`, `ToolExecutionResult`) and do not
  crash the runtime.
- Tool Bus does not authorize commands. Policy/authority/HITL remain mandatory
  runtime gates.

## Runtime integration points

- `build_runtime()` binds `ToolContractRegistry` into `ToolRuntime`.
- `AgenticRuntime.submit()` still validates contracts before policy/budget and
  validates outputs before verifier success.
- `ToolRuntime.dispatch()` now delegates to `ToolBus.execute()`.
- Trace remains runtime-owned; Tool Bus does not write trace directly.
