# P1.2 — Prompt System Seed Report

**Date:** 2026-06-17  
**Status:** PASS (local verification)

## 1. Summary

P1.2 creates the governed prompt system foundation. Prompts now live as versioned YAML manifests under `prompts/`, load through `PromptRegistry`, validate ownership/version/task/model/policy metadata, render through explicit `{{ variable }}` placeholders, and produce trace-safe summaries without storing raw rendered prompts by default.

The implementation preserves the core law: **Entity proposes. Runtime disposes.** Prompts can propose language only; they do not grant authority, execute tools, modify files, request secrets, or override Runtime/Custos-style validators.

## 4. Prompt manifest schema

Each manifest includes:

- `id`, `version`, `owner`, `status`, `purpose`, `description`
- `allowed_model_profiles`, `allowed_tasks`, `risk_tier`
- `input_schema`, `output_schema`
- `policy`
- `forbidden`
- `evals`
- `template`

Templates use simple `{{ variable }}` placeholders and fail safely when variables are missing through the Python API.

## 5. Prompt laws

- Prompts are inspectable runtime assets, not hidden hardcoded strings.
- Prompts may not expand authority.
- Prompts may not request secrets.
- Planning prompts may not request tool execution or file modification.
- Core prompts must forbid policy override behavior.
- Prompt manifests and rendered prompts reject obvious raw secret-like values.
- Prompts propose language only; Runtime/Custos-style validators decide.

## 6. Prompt rendering behavior

`PromptTemplate.render()`:

- accepts `PromptRenderContext`
- replaces `{{ variable }}` placeholders
- raises `PromptRenderError` on missing variables
- raises `PromptRenderError` when rendered text contains obvious raw secret-like values
- returns raw rendered text only when `include_raw_prompt=True`
- defaults to no raw rendered prompt storage

`LLMRepoPlanner` now accepts an optional prompt registry. If supplied, it renders `repo_planner`; otherwise the existing P0.21 hardcoded fallback remains unchanged.

## 7. Prompt trace summary behavior

`PromptTraceSummary` includes:

- `prompt_id`
- `version`
- `owner`
- `purpose`
- `allowed_model_profiles`
- `allowed_tasks`
- `risk_tier`
- `template_hash`
- `rendered_hash`
- `variables_used`
- `raw_prompt_stored: false`
- optional bounded `rendered_preview_redacted`

The CLI render command omits rendered previews and prints metadata plus hashes only.

## 8. Secret redaction behavior

Prompt outputs reuse `SecretRedactor` from P1.1. Prompt manifests reject obvious raw secrets such as `sk-*`, Bearer tokens, and env-key assignments. Rendered prompt summaries redact bounded previews, and CLI prompt output avoids raw prompt text.

## 9. Model profile validation behavior

`PromptRegistry` can accept a P1.1 `ModelConfigBundle`.

- With `validate_model_profiles=True`, every `allowed_model_profiles` entry must exist in `bundle.profiles`.
- Without config, prompt loading still works and API keys are not required.
- Default CLI validation loads `agent/config/` and validates prompt profile references.

## 10. CLI commands

## 13. Known limitations

- YAML support remains the project’s constrained stdlib subset; multiline YAML scalar blocks are not supported.
- Prompt trace summaries are produced at render time but not yet appended to the main trace ledger.
- Repo planner prompt registry use is optional and constructor-driven; no global runtime prompt config is introduced yet.
- `patch_synthesizer` is a manifest seed only. P1.2 does not implement LLM patch synthesis.
- No integrations, MCP, plugins, browser/network tools, desktop UI, mobile UI, or terminal TUI are included.
