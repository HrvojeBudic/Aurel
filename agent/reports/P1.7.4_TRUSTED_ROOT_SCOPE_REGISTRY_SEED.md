## 1. Purpose

P1.7.4 establishes stable, deterministic, JSON-safe, hash-ready trusted root and scope registry objects. It represents declared root boundaries and declared grant/deny scope state without resolving authority, checking the filesystem, detecting path escapes, changing sandbox behavior, or enforcing permissions.

Core law: registry means declare, not authorize. Trusted root is not permission. Scope grant is not runtime authority. Scope deny is not enforcement. Registry seed is not sandbox.

## 6. Registry Boundary Summary

- Trusted root does not mean permission.
- Scope grant does not mean runtime authority.
- Scope deny does not mean enforcement.
- Registry seed does not mean sandbox.
- Repo root declaration does not mean executable-safe.
- Workspace root declaration does not mean sandbox permission.
- Operator-approved declaration does not override policy.
- Upload boundary does not make uploaded content trusted.
- Denied root declaration does not enforce runtime blocking yet.

## 7. Governance Boundary

P1.7.4 creates the Trusted Root & Scope Registry Seed; it does not add trusted root authority resolution, path/source resolver behavior, path escape detection, path permission enforcement, filesystem security, runtime enforcement, Ledger writes, approval activation, CLI/TUI binding, Shell UI, filesystem reads, symlink resolution, or sandbox behavior changes.

Additional boundary confirmations:

- No `AgenticRuntime.submit` call or import.
- No runtime, sandbox, approval, policy, tools, trace, CLI, or CLI module changes.
- No file reads, path existence checks, permission checks, stat calls, symlink resolution, source/path content scans, or live filesystem state in hashes.
- Registry hashes are deterministic and order-insensitive for roots, grants, and denies.
