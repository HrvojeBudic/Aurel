**Status:** COMPLETE

**Successor:** P1.6.16 — Policy Test Harness

## Purpose

P1.6.15 records shadow policy violation evidence; it does not enforce policy decisions, write to the Ledger, activate approvals, block commands, or change runtime sandbox behavior.

## Why Violation Trace Exists

Custos shadow governance produces mismatch signals between P0 runtime posture and Custos `WOULD_*` outcomes, plus structural gaps (missing context, adapter errors, incomplete traces, unresolved conflicts). P1.6.15 formalizes these as deterministic, hash-ready violation evidence envelopes for audit and future Ledger compatibility without coupling to enforcement.

## Relationship to P1.6.12 Runtime Projection

`project_policy_resolution_against_runtime()` now attaches violation metadata (`violation_trace_id`, `violation_hash`, `violation_type`, `violation_severity`, `violation_status`) to `PolicyShadowProjection` before final `projection_hash` computation. Projection remains `mode=shadow_only`, `enforced=false`.

## Relationship to P1.6.13 Conflict Algebra

Violation envelopes include `conflict_hash`, `conflict_codes`, and `strictest_decision_rank` extracted from `ResolvedPolicySet.conflict_resolution`. Missing conflict metadata emits explicit `reason_codes` without crashing.

## Relationship to P1.6.14 Resolution Trace

Violation envelopes bind `policy_resolution_trace_id` and `policy_resolution_hash` from P1.6.14 trace metadata. Missing resolution trace triggers `POLICY_TRACE_INCOMPLETE` classification.

## Severity and Status Model

**Severity:** `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` — priority-based selection with conservative upgrades.

**Status:** Default `SHADOW_ONLY` / `CANDIDATE`; alignment-only cases use `OBSERVED`; unknown vocabulary uses `NEEDS_OPERATOR_REVIEW`.

## Violation Trace Envelope Schema

Key fields on `PolicyViolationTraceEvent`: `violation_trace_id`, `violation_hash`, `violation_type`, `violation_severity`, `violation_status`, `policy_resolution_trace_id`, `policy_resolution_hash`, `conflict_hash`, `projection_hash`, `runtime_snapshot_hash`, `context_hash`, `registry_hash`, `p0_verdict`, `custos_shadow_action`, `strictest_decision_rank`, `alignment_status`, `shadow_only=true`, `enforced=false`, `reason_codes`, `conflict_codes`, `source_family_ids`, `source_card_ids`, `metadata`.

## Hash and Canonicalization Strategy

- `policy_violation_canonical_dict(event, include_hash=False)` — sorted keys, sorted list fields
- `policy_violation_hash(event)` — SHA-256 over JSON canonical form
- `violation_trace_id` = `violation_hash` (deterministic)
- `violation_hash` excluded from hashed body (same pattern as P1.6.14)
- Shuffled lists produce identical hashes

## Resolution Trace Binding

`bind_policy_violation_from_resolution()` extracts trace, conflict, and context fields from `ResolvedPolicySet`. Resolver `_attach_violation_metadata()` stores optional `violation_trace`, `violation_trace_hash`, `violation_trace_id` on `ResolvedPolicySet` (include_hash only, not in canonical body hash).

## Runtime Projection Metadata Binding

Projection builds interim hash, classifies violation via binding helper, attaches violation fields, then recomputes `projection_hash` including violation metadata.

## Shadow-Only Guarantee

- `shadow_only=True` and `enforced=False` enforced in `PolicyViolationTraceEvent.__post_init__`
- No `AgenticRuntime` import in violation module
- No Ledger write, no command block, no approval activation

## Non-Enforcement Proof

Violation objects have no `enforce`, `block`, `apply`, `approve`, `submit`, or `write_ledger` methods. Runtime projection and resolver hooks only attach metadata.

## Why This Is Not Full Ledger Enforcement

No `AurelTraceLog` append, no `trace.py` integration, no runtime authorization change. Evidence objects are future-compatible but not Ledger-integrated.

## Known Limitations

1. Resolver-only violation envelopes lack full P0/Custos mismatch without runtime snapshot
2. `projection_hash` in violation envelope uses interim projection hash (pre-violation attachment)
3. No `ObservationEnvelope.artifacts` direct violation field beyond projection metadata
4. `POLICY_RESOLUTION_INCONSISTENT` reserved — canonical vs trace-hash comparison removed (different semantic hashes)
