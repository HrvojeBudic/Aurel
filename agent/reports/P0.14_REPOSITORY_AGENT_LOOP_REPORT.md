# P0.14 Repository Agent Loop Report

Date: 2026-06-17

## Summary

P0.14 adds the first controlled repository coding loop. The loop builds bounded
repository context, creates an explicit plan, applies small patches through the
governed Runtime/Tool Bus path, runs tests, records bounded repair attempts, and
returns a structured `CodeTaskReport`.

This is intentionally not a fully autonomous software engineer.

## Repository agent architecture

- `RepoTaskRequest` describes the objective, repo path, path constraints, max changed files, max repair iterations, test command, and write-approval preference.
- `RepoContextBuilder` detects the repo root, reads bounded metadata/docs/files, skips secret-like files, truncates large files, and respects allowed/disallowed paths.
- `CodeTaskPlanner` produces an explicit `RepoTaskPlan` with inspect/patch/test steps, risk level, expected tests, and optional patch plans.
- `PatchExecutor` applies `write_file` or `patch_file` by submitting `CommandEnvelope` actions to `AgenticRuntime`.
- `TestRunnerAdapter` runs tests through the runtime using `run_tests` when possible and `run_shell` for command-shaped test invocations.
- `TestFailureAnalyzer` performs simple deterministic failure parsing.
- `RepairLoop` caps repair attempts and records every attempt.
- `RepositoryAgentLoop.run()` returns `CodeTaskReport`.

## Loop stages

1. Build bounded repository context.
2. Create and validate an explicit plan before writes.
3. Apply at most the requested number of file changes.
4. Run the requested test command.
5. Analyze failure output.
6. Stop after bounded repair attempts.
7. Produce a structured final report.

## Safety boundaries

- No git commit, git push, remote, browser, network, delete, or UI functionality.
- No vendor tool-calling.
- No multi-agent orchestration.
- Patch/test execution goes through `AgenticRuntime.submit()`.
- Runtime policy, HITL, budget, sandbox, verifier, trace, and memory governance remain authoritative.
- Repository context reads are bounded and skip secret-like files by default.
- Paths are constrained to the repo root and request path allow/deny lists.

## Runtime / Tool Bus integration points

- `PatchExecutor` submits `patch_file` / `write_file` commands.
- `TestRunnerAdapter` submits `run_tests` / `run_shell` commands.
- Runtime trace records those command transitions.
- Runtime memory governance records command summaries as before.
- The repository loop writes a best-effort candidate memory summary for the final report only; it does not promote memory.

## CLI usage

Plan-only default:

```bash
python -m agentic_runtime.cli repo-task "replace 'old' with 'new' in src/file.py"
```

Apply mode:

```bash
python -m agentic_runtime.cli repo-task "replace 'old' with 'new' in src/file.py" --apply
```

Optional scope and tests:

```bash
python -m agentic_runtime.cli repo-task "replace 'x' with 'y' in src/a.py" \
  --allowed-path src \
  --test-command "python3 -m pytest tests/test_a.py -q" \
  --apply
```

## Known limitations

- Planner is deterministic and intentionally narrow; it recognizes small quoted replacement tasks.
- Context building is bounded local inspection, not a full semantic code index.
- Repair analysis is simple and does not claim certainty.
- The loop does not expand scope automatically after failures.
- Default sandbox remains `UnsafeLocalSandbox`, which is not a production security boundary.
