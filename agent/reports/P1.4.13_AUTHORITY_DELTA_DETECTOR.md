# P1.4.13 — Authority Delta Detector

## 1. Summary

P1.4.13 adds the Authority Delta Detector to Aurel's identity layer. The detector compares two attested canonical states and detects whether authority, scope, risk ceiling, human oversight, tool permissions, capability status, claim status, or doctrine status changed in a way that matters.

P1.4.13 detects and reports authority deltas. It does NOT grant consent, approve changes, or execute tools.

## 5. Unified Implementation

Single coherent module at `src/agentic_runtime/identity/authority_delta.py` (~1120 lines) containing:

### Domain Model

- `AuthorityDeltaType` — 30 enum values covering authority scope, risk ceiling, oversight, tool permissions, write scope, external effect, capability/claim/doctrine status, source validation, validator/schema changes
- `AuthorityDeltaSeverity` — 5 levels: INFO, LOW, MEDIUM, HIGH, CRITICAL
- `AuthorityDelta` — frozen dataclass with delta_id, delta_type, severity, source_kind, field_path, old/new values, attestation refs, consent/evidence flags, reason, blockers, warnings
- `AuthorityDeltaInput` — frozen dataclass with source_kind, old/new canonical objects, optional attestation references
- `AuthorityDeltaReport` — frozen dataclass with report_id, deltas, highest_severity, consent/evidence flags, summary, safe_to_auto_accept, attestation IDs

### Authority Surface Extraction

`extract_authority_surface(source_kind, canonical_object)` returns a flat dict of authority-relevant field paths to JSON-safe values.

- Dictionaries are recursively descended, but authority field values are captured directly
- Dataclasses and objects with `__dict__` are supported
- Kind-specific field sets (e.g., `_OPERATOR_CONTRACT_FIELDS`, `_AGENT_IDENTITY_CARD_FIELDS`) 
- Universal authority fields (risk_ceiling, requires_human_approval, allowed_tools, etc.)
- Keyword-based matching for unknown but authority-flavored fields

### Semantic Delta Classification

`classify_authority_delta(field_path, old_value, new_value, source_kind)` classifies by authority meaning:

- Risk ceiling: upward → RISK_CEILING_INCREASED
- Human approval: True→False → OVERSIGHT_WEAKENED, False→True → OVERSIGHT_STRENGTHENED
- Constitutional boundaries (`cannot_*`, `aurel_can_*`, `require*`, etc.): True→False → OVERSIGHT_WEAKENED
- Allowed_tools addition: classified as EXTERNAL_EFFECT_ADDED, WRITE_SCOPE_ADDED, or TOOL_PERMISSION_ADDED based on conservative token heuristics
- Claim status escalation using CLAIM_STATUS_ORDER
- Doctrine status escalation using DOCTRINE_STATUS_ORDER
- Capability status escalation using CAPABILITY_STATUS_ORDER
- Validation status downgrades: SOURCE_VALIDATION_DOWNGRADED
- Validator/schema changes: VALIDATOR_CHANGED, SCHEMA_VERSION_CHANGED
- Authority scope: AUTHORITY_SCOPE_ADDED/REMOVED

### Severity Resolution

`resolve_authority_delta_severity(delta_type, old_value, new_value)` maps to severity:

- OVERSIGHT_WEAKENED → CRITICAL
- EXTERNAL_EFFECT_ADDED → CRITICAL
- RISK_CEILING_INCREASED → HIGH (or CRITICAL if target is "critical")
- CLAIM_STATUS_ESCALATED → HIGH/CRITICAL (depending on target)
- DOCTRINE_STATUS_ESCALATED → HIGH/CRITICAL (depending on target)
- CAPABILITY_STATUS_ESCALATED → HIGH/CRITICAL (depending on target)
- SOURCE_VALIDATION_DOWNGRADED → HIGH
- WRITE_SCOPE_ADDED → HIGH
- AUTHORITY_SCOPE_ADDED → HIGH
- Reductions/de-escalations → INFO

### Consent/Evidence Requirements

- `authority_delta_requires_consent()`: HIGH/CRITICAL severity or any authority expansion type → True
- `authority_delta_requires_evidence()`: status escalations, validation downgrades, validator/schema changes → True

### Conservative Tool Classification

External-effect tokens: `send_email`, `email`, `delete_file`, `remove_file`, `make_payment`, `payment`, `post_publicly`, `social_post`, `publish`, `api_write`, `external_api_write`, `webhook`, `deploy`, `shell_exec`, `subprocess`, `network_write`

Write tokens: `write`, `write_file`, `filesystem_write`, `delete`, `delete_file`, `remove_file`, `save`, `patch`, `replace`

The heuristic is conservative — any tool matching external-effect tokens is classified as EXTERNAL_EFFECT_ADDED with CRITICAL severity.

## 7. Delta Type Model

30 enum values in `AuthorityDeltaType`:

| Category | Types |
|---|---|
| Scope | AUTHORITY_SCOPE_ADDED, AUTHORITY_SCOPE_REMOVED |
| Risk | RISK_CEILING_INCREASED, RISK_CEILING_DECREASED |
| Oversight | OVERSIGHT_WEAKENED, OVERSIGHT_STRENGTHENED |
| Tools | TOOL_PERMISSION_ADDED, TOOL_PERMISSION_REMOVED, WRITE_SCOPE_ADDED, WRITE_SCOPE_REMOVED, EXTERNAL_EFFECT_ADDED, EXTERNAL_EFFECT_REMOVED |
| Status | CAPABILITY_STATUS_ESCALATED/DEESCALATED, CLAIM_STATUS_ESCALATED/DEESCALATED, DOCTRINE_STATUS_ESCALATED/DEESCALATED |
| Validation | SOURCE_VALIDATION_DOWNGRADED/UPGRADED, VALIDATOR_CHANGED, SCHEMA_VERSION_CHANGED |
| Catch-all | UNKNOWN_AUTHORITY_CHANGE |

## 8. Severity Model

5 levels with semantic meaning:

| Severity | Meaning |
|---|---|
| INFO | Reduction, de-escalation with no risk increase |
| LOW | Small non-external scope change |
| MEDIUM | Tool permission addition, validator/schema change |
| HIGH | Authority expansion, write scope, status escalation |
| CRITICAL | Oversight weakened, external effect added, high-risk escalation |

## 9. Consent Requirement Marker

`authority_delta_requires_consent(delta)` returns True when:
- Severity is HIGH or CRITICAL
- Delta type is any authority expansion:
  - AUTHORITY_SCOPE_ADDED
  - RISK_CEILING_INCREASED
  - OVERSIGHT_WEAKENED
  - TOOL_PERMISSION_ADDED
  - WRITE_SCOPE_ADDED
  - EXTERNAL_EFFECT_ADDED
  - CAPABILITY/CLAIM/DOCTRINE_STATUS_ESCALATED
  - SOURCE_VALIDATION_DOWNGRADED

## 10. Evidence Requirement Marker

`authority_delta_requires_evidence(delta)` returns True when:
- Claim, capability, or doctrine status escalates
- Source validation downgrades
- Validator or schema version changes
- Production eligibility or implemented status keywords appear in the new value

## 11. Attestation Integration

`AuthorityDeltaReport` carries `old_attestation_id` and `new_attestation_id` when `SourceAttestation` objects are provided via `AuthorityDeltaInput`. Individual `AuthorityDelta` records also carry the attestation references.

## 15. Known Limitations

- Tool permission classification uses conservative string heuristics. Refined tool metadata and risk scoring should replace these in P1.6/P6/P7.
- Authority surface extraction supports dicts and dataclasses but not all possible Python object shapes.
- Attestation references are carried in delta reports but not yet used for cryptographic delta verification (requires signing keys, P1.4.15 or later).
- The `safe_to_auto_accept` flag is purely based on severity and consent requirements. It does not consult runtime state, tool availability, or environment context.
- CLIP only supports `compare` (file-based). `compare-attested` (using actual attestation envelopes) and `verify-bundle` commands are planned for future iteration.

## 17. P1.4.14 Handoff

P1.4.14 Operator Consent Binding should build on P1.4.13's delta reports:

- The consent-required markers (`requires_operator_consent: true`) signal which deltas need human approval
- The evidence-required markers (`requires_evidence: true`) signal which deltas need supporting evidence
- The attestation references (`old_attestation_id`, `new_attestation_id`) link deltas to P1.4.12 source attestations
- The `safe_to_auto_accept` flag tells P1.4.14 whether auto-acceptance is semantically dangerous

P1.4.13 prepares Authority Delta Detector. P1.4.14 binds Operator consent to those deltas. P1.4.13 does not grant consent, approve changes, or execute tools.
