# P1.6.11 Policy Resolution Context & Registry Binding Report

Date: 2026-06-23
Status: ACTIVE implementation complete; validation passed

## 1. Purpose

P1.6.11 adds the deterministic bridge between explicit policy-card lists, runtime-like request metadata, and Custos v0 shadow resolution.

P1.6.11 binds policy-card discovery and context assembly to the Custos v0 resolver, but it does not enforce resolver outcomes through AgenticRuntime.submit().

## 2. Why registry binding exists

P1.6.10 could judge explicit cards passed directly to `resolve_policy_cards()`. It could not yet assemble the relevant lawbook from policy-card storage/list surfaces or normalize runtime-like request metadata before judgment.

P1.6.11 provides that missing bridge:

```text
policy cards + runtime-like metadata
  -> PolicyResolutionContext
  -> PolicyCardRegistry
  -> applicable cards
  -> Custos resolver
  -> ResolvedPolicySet in SHADOW mode
```

## 3. Relationship to P1.6.10 resolver

P1.6.10 remains the judgment engine. P1.6.11 does not rewrite the seven family adapters, the strictest-wins aggregation rule, or SHADOW-only enforcement mode. It adds `resolve_policy_cards_from_registry()` and `PolicyRuntimeResolver.resolve_from_registry()` so registry-selected applicable cards can feed the existing resolver.

## 4. Relationship to P1.6.10H truth hotfix

P1.6.10H corrected runtime/security/coverage/documentation truth before registry binding. P1.6.11 preserves that truth: sandbox policy cards and Custos resolver output remain semantic/shadow-only and do not change runtime sandbox behavior.

## 5. PolicyCardRegistry design

Implemented in `src/agentic_runtime/policy_cards/registry.py`.

Key behavior:

- explicit in-memory registry only
- accepts typed resolver-ready card instances/lists
- rejects dict loading in the registry layer
- stable card ordering using resolver family order, card ID, version, scope, and canonical hash
- duplicate card ID plus same hash deduplicates deterministically
- duplicate card ID plus different hash raises `PolicyCardRegistryValidationError`
- family lookup via `get_by_family()`
- scope lookup via `get_by_scope()`
- source hash collection via `source_hashes()`
- stable `canonical_dict()` and `canonical_hash()`

No database, filesystem discovery, runtime import, or enforcement path is implemented.

## 6. Context binding design

Implemented in `src/agentic_runtime/policy_cards/context_binding.py`.

Public helpers:

- `build_policy_resolution_context()`
- `normalize_resolution_context()`
- `context_from_command_like()`
- `context_from_tool_invocation_like()`
- `context_from_runtime_request_like()`

Dict inputs are closed-world against the known context/binding field set. List/set-like fields are normalized into sorted tuples. Metadata must be JSON-safe and cannot contain dangerous policy-control keys. Missing `context_id` is generated deterministically from normalized content.

The binding helpers import no runtime classes and execute no commands.

## 7. Risk mapping seed

Implemented in `src/agentic_runtime/policy_cards/risk_mapping.py`.

Public helpers:

- `normalize_risk_tier()`
- `map_runtime_risk_to_policy_tier()`
- `map_approval_risk_to_policy_tier()`
- `map_identity_risk_to_policy_tier()`

The mapping seed translates known runtime (`TRIVIAL`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), approval (`R0`-`R6`), policy-card, and identity/autonomy risk strings into P1.6 `RiskTier` values. Unknown present values map conservatively to R5 with explicit reason code `UNKNOWN_RISK_CONSERVATIVE`. Unsupported value types raise `PolicyRiskMappingError`.

This is not full risk enum unification.

## 8. Applicability filtering rules

Registry applicability is deterministic and transparent via `PolicyCardApplicability` reason codes.

Family signals:

- risk tier cards apply when `risk_tier` is present
- human oversight cards apply when `risk_tier` or `requested_action` is present
- data residency cards apply when `data_classes` are present
- tool permission cards apply when `tool_name` or `tool_category` is present
- memory write cards apply when `memory_write_intent` is true
- prompt cards apply when `prompt_source_types` are present
- sandbox cards apply when sandbox/execution metadata is present

Scope signals support global/runtime, tool, model, memory, prompt, sandbox, agent, workflow, and business scope where context fields are available. Missing context produces `SKIPPED_CONTEXT_MISSING`; scope mismatch produces `SKIPPED_SCOPE_MISMATCH`.

## 9. Determinism guarantees

- Same cards and same context produce the same registry canonical hash and resolver canonical hash.
- Shuffled card input produces the same registry order and resolver result.
- List/set-like context fields are sorted.
- Registry canonical serialization uses sorted JSON keys and compact separators.
- No timestamps, random UUIDs, filesystem iteration, or runtime state enter canonical hashes.

## 10. Resolver integration path

`resolve_policy_cards_from_registry(context, registry)` calls `registry.get_applicable(context)` and passes the resulting explicit card tuple to `resolve_policy_cards()`.

`PolicyRuntimeResolver.resolve_from_registry(context, registry)` provides the same path through the resolver facade.

No-card/no-applicable-card behavior remains conservative through the existing resolver aggregation path.

## 11. Shadow-only guarantee

All resolver integration remains SHADOW mode. Outputs are `WOULD_*` decisions on `ResolvedPolicySet`.

P1.6.11 does not:

- modify `AgenticRuntime.submit()`
- block commands
- activate approvals
- change sandbox runtime behavior
- enforce policy-card decisions
- project decisions into runtime adapters

## 14. Known limitations

- Applicability filtering is intentionally conservative and MVP-level.
- No Policy Conflict Algebra is implemented.
- Risk mapping is a seed only; it does not unify every risk enum across the repository.
- Registry does not load card dicts or files; callers must use existing family loaders first.
- Context binding is a projection helper, not a runtime hook.
- Human oversight applicability is scoped to risk/action signals for P1.6.11.

## 15. What was deliberately not implemented

- No P1.6.12 enforcement adapter.
- No active runtime enforcement.
- No `AgenticRuntime.submit()` behavior change.
- No command blocking.
- No approval activation.
- No sandbox runtime bridge.
- No database registry.
- No broad filesystem policy-card discovery.
- No full Policy Conflict Algebra.
- No full risk enum migration.
- No Golden Thread B.
- No identity command refactor.
