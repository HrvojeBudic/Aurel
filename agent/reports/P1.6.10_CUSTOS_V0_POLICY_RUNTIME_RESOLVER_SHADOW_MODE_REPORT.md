# P1.6.10 — Custos v0 Policy Runtime Resolver / Shadow Mode Report

**Date:** 2026-06-23
**Status:** COMPLETE (shadow mode only)
**Domain:** P1 — AurelCore Foundation
**Section:** P1.6 — Policy Cards & Behavioral Contracts

> **P1.6.10 opens the Custos v0 resolver path in shadow mode. It interprets policy
> cards but does not yet enforce them through `AgenticRuntime.submit()`.**

---

## 1. Purpose

Provide the first runtime-shaped component that *interprets* the P1.6 policy-card
families into a single, deterministic, shadow-mode judgment. The resolver answers
one question: **"If policy-card enforcement were active, what would happen?"** —
expressed as `WOULD_ALLOW`, `WOULD_WARN`, `WOULD_REQUIRE_APPROVAL`, or `WOULD_DENY`.

## 2. Strategic reason for the resolver

A strategic evaluation concluded Aurel has strong policy-card *semantics* but no
policy *consequence*. P1.6.10 is the first step from vocabulary to adjudication. It
deliberately stops short of enforcement so judgment quality can be observed and
tuned before any command is ever blocked. Aurel's law is "entity proposes, runtime
disposes"; P1.6.10 does not yet dispose — it teaches Custos how to judge before it is
allowed to enforce.

## 3. Relationship to P1.6.0–P1.6.9 policy cards

The resolver consumes the existing typed cards unchanged:

- Risk Tier (P1.6.3), Human Oversight (P1.6.4), Data Residency (P1.6.5), Tool
  Permission (P1.6.6), Memory Write (P1.6.7), Prompt (P1.6.8), Sandbox (P1.6.9).
- The sandbox family reuses the resolver-ready `evaluate_sandbox_policy_decision()`
  / `SandboxPolicyDecisionInput` / `SandboxPolicyDecision` structures that P1.6.9
  built explicitly "for P1.6.10 Custos consumption".
- No card model, schema, validation, serialization, or hash was modified.

## 4. What P1.6.10 implements

New files (chosen location: `src/agentic_runtime/policy_cards/`, alongside the cards,
because every card family already lives there and the resolver is a pure consumer of
those modules — no separate `policy_resolver/` package was warranted):

- **`resolution_context.py`** — `EnforcementMode` (SHADOW + reserved ENFORCE/SIMULATE);
  `PolicyResolutionContext` frozen dataclass with closed-world `from_dict`,
  deterministic `to_canonical_dict`, and SHA-256 `context_hash`.
- **`resolution_result.py`** — `PolicyFamily`, `FamilyDecision`, `ShadowAction`,
  `PolicyFamilyDecision`, `ResolvedPolicySet` with deterministic canonical
  serialization, SHA-256 `canonical_hash`, and `would_*` predicates.
- **`resolver.py`** — seven family adapters, strictest-wins `aggregate_family_decisions`,
  `resolve_policy_cards()`, and the `PolicyRuntimeResolver` facade.
- **`errors.py`** — 5 resolver error classes (all used in code/tests).
- **`__init__.py`** — public exports.
- **`tests/test_policy_resolver_p1610.py`** — 51 tests.

## 5. What P1.6.10 deliberately does NOT enforce

- `AgenticRuntime.submit()` is **untouched**; no command is blocked, paused, or mutated.
- No active enforcement, no runtime approval gating, no instruction-hierarchy /
  sandbox / memory / tool runtime blocking.
- `ENFORCE` and `SIMULATE` modes are reserved names only; passing them is rejected
  fail-closed (`PolicyResolutionValidationError`). No enforcement code path exists.
- No full Policy Conflict Algebra, no registry binding, no card discovery, no Golden
  Thread B, no runtime dependencies.

## 6. Shadow mode semantics

`enforcement_mode` is always `SHADOW`. The aggregate and every family decision expose
an `effective_shadow_action` using explicit `WOULD_*` values. The result is a pure data
object with no enforcement surface (`enforce` / `apply` / `block` / `submit` attributes
are absent and asserted absent in tests).

## 7. PolicyResolutionContext summary

A frozen, deterministic description of a proposed action: identity fields
(`context_id`, `agent_id`, `operator_id`, `command_id`, `command_summary`),
action descriptors (`requested_action`, `tool_name`, `tool_category`, `command_class`,
`risk_tier`, `requested_sandbox_backend`, `requested_filesystem_scope`,
`requested_egress`, `requested_model`), list fields (`requested_paths`,
`requested_network_targets`, `prompt_source_types`, `data_classes`), and boolean intent
flags (`memory_write_intent`, `touches_secrets`, `writes_files`, `runs_shell`,
`installs_packages`, `requires_network`), plus descriptive `metadata`.
Closed-world `from_dict` rejects unknown fields, invalid risk tiers, non-boolean flags,
and dangerous metadata keys. List fields are sorted in the canonical form for stable
hashing.

## 8. ResolvedPolicySet summary

`resolution_id` (deterministic from `context_hash` + sorted source hashes),
`context_hash`, `enforcement_mode = SHADOW`, `overall_decision`,
`effective_shadow_action`, `family_decisions`, aggregated `reason_codes`, `warnings`,
`violations`, `approval_requirements`, `applicable_card_ids`, `source_hashes`, and
`canonical_hash` (computed over everything except itself). No timestamps are used, in
keeping with the deterministic-artifact convention of the policy-card modules.

## 9. Family adapter summary

| Family | Conservative behavior |
|--------|-----------------------|
| Risk Tier | denied tier → DENY; approval/explicit-confirmation tiers → REQUIRE_APPROVAL; evidence tier → WARN; above card ceiling → DENY; unknown/undefined → WARN/REQUIRE_APPROVAL |
| Human Oversight | deny mapping → DENY; approval/confirmation/dual/board → REQUIRE_APPROVAL; review/notify → WARN; none → ALLOW; no mapping → REQUIRE_APPROVAL; external-egress escalation |
| Data Residency | forbidden zone or blocked egress of a data class → DENY; local-only data with external intent → DENY; approval-required egress → REQUIRE_APPROVAL; unknown sensitive class → REQUIRE_APPROVAL; unknown class → WARN; no data classes → NOT_APPLICABLE |
| Tool Permission | matched DENY → DENY; approval/confirmation → REQUIRE_APPROVAL; sandbox/read-only/local/conditional → WARN; unmatched → REQUIRE_APPROVAL; no tool context → NOT_APPLICABLE |
| Memory Write | default forbidden → DENY; review/confirmation rules → REQUIRE_APPROVAL; evidence/provenance/candidate rules → WARN; default-deny w/o allow → REQUIRE_APPROVAL; no write intent → NOT_APPLICABLE |
| Prompt | deny/forbidden or untrusted-instruction → DENY; high/critical injection or review → REQUIRE_APPROVAL; medium injection or context-only constraints → WARN; unknown untrusted source → REQUIRE_APPROVAL; no sources → NOT_APPLICABLE |
| Sandbox | reuses `evaluate_sandbox_policy_decision`: not allowed + violations → DENY; allowed + approval → REQUIRE_APPROVAL; allowed + no approval → ALLOW; no execution intent → NOT_APPLICABLE |

## 10. Strictest-wins MVP rules

`DENY > REQUIRE_APPROVAL (= ERROR, conservative) > WARN > ALLOW > NOT_APPLICABLE`.
Any DENY → overall DENY. Else any ERROR/REQUIRE_APPROVAL → REQUIRE_APPROVAL (ERROR adds
`ADAPTER_ERROR_CONSERVATIVE`, never swallowed). Else any WARN → WARN. Else ALLOW. No
applicable cards (empty list or all NOT_APPLICABLE) → conservative WARN with
`NO_APPLICABLE_CARDS` (and `NO_CARDS_PROVIDED` when the list is empty) — never a silent
ALLOW.

## 11. Determinism / hash strategy

Stable sorting of cards (by id), reason codes, warnings, violations, approval
requirements, family decisions (by family), and context list fields. Enum values
normalize to strings. `resolution_id` and both hashes are pure functions of
context + card hashes; no timestamps or random UUIDs enter any canonical hash. Same
input/cards → identical `resolution_id` and `canonical_hash` (asserted in tests).

## 14. Known limitations

- Adapters are MVP-conservative, not full semantic engines; deep field coverage and the
  full Policy Conflict Algebra are later phases (P1.6.11+/P1.6.13).
- Applicability is intent-driven from the context (e.g., memory requires
  `memory_write_intent`); richer scope matching arrives with registry binding (P1.6.11).
- The context carries data classes / tool identity as strings; tighter typed binding to
  card enums is deferred to avoid coupling.
- Full-suite, coverage, and `mypy src/agentic_runtime` should be run before commit to
  confirm no regression and coverage ≥ 75%.
