# P0.21 LLM Planning Bridge Report

_Date: 2026-06-17_

## Summary

P0.21 adds an optional LLM planning bridge for `RepositoryAgentLoop`. The LLM can only produce a structured repository task plan. It cannot execute tools, invoke vendor tool-calling, write files, run tests, or bypass the runtime.

Default behavior remains deterministic. Offline tests use `MockProvider`; no API keys are required.

## Planner Architecture

`RepositoryAgentLoop` now selects planning based on `RepoTaskRequest.planner_mode`:

1. Build bounded repo context with `RepoContextBuilder`.
2. Produce a `RepoTaskPlan` using deterministic or LLM planning.
3. Validate the plan with `RepoPlanValidator`.
4. Submit patches/tests through the unchanged governed path.

Execution remains:

`RepositoryAgentLoop -> Runtime -> Tool Bus -> Approval -> Sandbox -> Verifier / Trace / Praxis`

## Planner Modes

- `deterministic`: existing planner behavior; default.
- `llm`: use `LLMRepoPlanner`; invalid/unavailable output fails safely as `planning_failed`.
- `hybrid`: try `LLMRepoPlanner`; if invalid/unavailable, fall back to deterministic planning and record `fallback_reason`.
- `dry_run`: produce plan/approval requirements only; no patch execution.

`CodeTaskReport` records planner mode, provider, planning errors, fallback reason, and plan assumptions.

## LLM Plan Schema

Required fields:

- `objective_summary`
- `files_to_inspect`
- `files_to_modify`
- `proposed_steps`
- `risk_level`
- `expected_tests`
- `requires_approval`
- `assumptions`
- `refusal_reason`

Each proposed step includes:

- `step_id`
- `action_type`: `inspect`, `patch`, `test`, `analyze`, or `report`
- `target_path` optional
- `tool_name` optional
- `reason`
- `expected_output`
- `risk_class`

## Validation Rules

`RepoPlanValidator` rejects:

- invalid JSON or missing required fields
- unexpected top-level/step fields
- disallowed paths
- path traversal through allowed/disallowed checks
- `files_to_modify` larger than `max_files_changed`
- test-file modifications unless explicitly allowed
- missing `expected_tests` for non-refusal plans
- empty executable plans without `refusal_reason`
- refusal plans that still include executable patch/test steps
- invalid risk/action values

Invalid LLM output becomes a structured planning failure, not an uncaught exception.

## Known Limitations

- LLM planning proposes plans only; patch synthesis remains deterministic and intentionally narrow.
- Real providers are optional and depend on local/API configuration; offline tests use `MockProvider`.
- `hybrid` fallback improves availability but does not make an invalid LLM plan valid; it records the fallback reason.
- Prompt context is bounded summaries/previews, not full repository state.
- Default sandbox remains a local demo boundary unless configured otherwise.
