## Purpose

P1.6.16 introduces a deterministic policy test harness for shadow governance validation; it does not enforce policy decisions, write to the Ledger, activate approvals, block commands, or change runtime sandbox behavior.

## Why Policy Test Harness Exists

P1.6.9–P1.6.15 built shadow governance primitives (resolver, conflict algebra, resolution trace, violation trace). P1.6.16 turns that stack into a testable subsystem: define scenarios, run the real shadow path, compare expected vs actual, and emit deterministic hashed reports — without coupling to runtime enforcement or CI rewrite.

## Relationship to P1.6.13 Conflict Algebra

Harness actuals read `conflict_resolution.conflict_codes` and `winning_rank` from resolver-attached metadata. Integration scenarios exercise strictness conflicts, adapter errors, and family-specific conflict taxonomies via `family_decisions` inputs.

## Relationship to P1.6.14 Resolution Trace

Harness actuals include `resolution_trace_hash` from `ResolvedPolicySet.resolution_trace_id`. Comparator flags `EXPECTED_TRACE_MISSING` when trace is expected but absent.

## Relationship to P1.6.15 Violation Trace

Harness actuals include `violation_hash` and `actual_violation_types` from resolution violation metadata or `bind_policy_violation_from_resolution()` for prebuilt resolutions. P0/Custos mismatch scenarios use `p0_verdict` + runtime projection.

## Harness Expected/Actual/Result/Report Schema

- **Actual:** shadow action, strictest rank, conflict/violation types, trace/violation/projection hashes, `shadow_only`, `enforced`, reason/conflict codes, sanitized metadata
- **Result:** verdict, actual, `expected_vs_actual`, failures, warnings, `canonical_hash`
- **Suite/Run/Report:** aggregated counts, coverage maps, `determinism_status`, `shadow_only_status`, `report_hash`

## Verdict and Failure Model

**Verdicts:** `PASS`, `FAIL`, `WARN`, `ERROR`, `SKIPPED`

**Failure types:** rank/action mismatch, conflict missing/unexpected, trace/violation missing, unexpected enforcement, non-deterministic hash, adapter/registry/context errors, policy design error, unsupported scenario.

Critical mismatches → `FAIL`. `UNEXPECTED_CONFLICT` alone → `WARN`.

## Expected-vs-Actual Comparator

`compare_policy_harness_expected_actual()` applies deterministic rules. `evaluate_policy_harness_case()` executes input, compares, optionally checks hash stability across repeated runs, and attaches canonical result hash.

## Deterministic Hash Strategy

- `policy_harness_case_hash()` — sorted tags, conflict types, violation types in canonical dict
- `policy_harness_result_hash()` — sorted actual fields, failures, warnings
- `policy_harness_report_hash()` — results sorted by `case_id`; report hash excludes run timestamp
- Metadata sanitized: no secrets, no command bodies

## Shadow-Only Guarantee

All harness actuals set `shadow_only=True`, `enforced=False`. Report includes `shadow_only_status`. No enforcement methods on harness types.

## Non-Enforcement Proof

Harness module does not import `AgenticRuntime`, `trace.py`, or Ledger writers. No block/apply/approve/write_ledger methods. Resolver hooks attach metadata only.

## Why This Is Not a pytest Replacement or CI Rewrite

The harness is a domain-specific shadow-governance scenario runner composable with pytest. It does not replace pytest discovery, reporting, or CI pipelines. Full-suite gates remain operator-run.

## Known Limitations

- Not all 15 spec matrix items have separate built-in module fixtures (scenarios live in tests)
