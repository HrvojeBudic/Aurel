## Praxis architecture

```
CommandResult / CodeTaskReport / approval / test / verifier
  → PraxisExperienceBuilder → PraxisExperience
  → PraxisCandidateGenerator → MemoryCandidate(s)
  → PromotionEvaluator (PromotionGate) → ProcedureCandidate / SkillCandidate
  → ReflexEligibilityCheck (governance still required)
  → MemoryFabric.request_write (CANDIDATE only, via adapter)
  → PraxisEventRecord trace
  → PraxisReport
```

### Contracts added

- `PraxisExperience`, `PraxisEvidence`, `PraxisOutcomeStatus`
- `MemoryCandidate`, `ProcedureCandidate`, `SkillCandidate` (Praxis layer)
- `PromotionDecision`, `PromotionReport`, `ReflexEligibilityCheck`
- `PraxisReport`, `PraxisMetabolism`

Praxis `SkillCandidate` is exported as `PraxisSkillCandidate` to avoid collision
with `core_types.SkillCandidate` used by `skills.py`.

## Memory candidate rules

| Outcome | Candidate types allowed |
|---------|-------------------------|
| Success | Episodic (+ procedural hint if test/verifier/report evidence) |
| Failure / denied / deferred | Diagnostic only |
| Partial | Diagnostic |
| No trace/evidence | Rejected |

Additional rules:

- Secrets redacted; summaries capped at 500 chars
- Failed runs cannot submit episodic/operational success memory via governance adapter
- Trust level conservative (low without evidence; medium/high only with test+verifier)
- All governance writes land at `MemoryTruthState.CANDIDATE` — never verified/canon

## Promotion gate behavior

1. **MemoryCandidate** — requires trace-backed experience
2. **ProcedureCandidate** — requires accepted memory candidates with evidence refs; diagnostic-only rejected
3. **SkillCandidate** — requires procedure with evidence + bounded steps
4. **ReflexEligibilityCheck** — eligible only for bounded low/medium risk skills with preconditions; high risk not reflex-eligible; `must_still_pass_*` flags always true

No automatic promotion to verified/procedural/canon memory.

## Repo agent integration

`RepositoryAgentLoop.run()` now attaches `CodeTaskReport.praxis_report` after every
terminal status (succeeded, failed, planned, dry_run, planning_failed). Successful
tasks may produce episodic candidates; failed tasks produce diagnostic candidates only.
Governance submission is best-effort through `submit_memory_candidate_to_governance`.

## Skill/reflex boundary

`bridge_skill_candidate_to_library()` returns a proposal dict only — it does **not**
register active skills or reflexes. Reflex eligibility explicitly documents that
policy, sandbox, verifier, and trace remain mandatory.

## Known limitations

- In-memory metabolism store only (no vector DB, RAG, or knowledge graph)
- No multi-experience pattern mining or automatic procedure synthesis
- Repeated repo tasks may re-submit similar candidates to governance
- Skill bridge does not wire into `SkillLibrary` lifecycle (OBSERVED→REFLEX)
- Promotion to verified/procedural/canon still requires existing P0.9 governance paths
