## Purpose

P1.6.13 introduces deterministic conflict algebra within the Custos shadow policy decision system. It normalizes policy family decisions into formal ranks, classifies conflicts between them, determines the "strictest valid outcome" according to defined rules, preserves all conflict evidence, and produces deterministic canonical payloads and hashes for conflict resolutions.

P1.6.13 formalizes Custos shadow conflict resolution through deterministic strictest-wins algebra; it does not enforce policy decisions, activate approvals, block commands, or change runtime sandbox behavior.

## Core Law

- The strictest valid policy outcome wins.
- Ambiguity must be explicit.
- Adapter errors must be explicit.
- Unknown context must be conservative.
- Tie-breaks must be deterministic.
- Everything must be hash-ready and trace-ready.
- Nothing is enforced.

## Strictest-Wins Rank Order

| Rank | Value | Wins over |
|------|-------|-----------|
| ERROR | 5 | Everything |
| DENY | 4 | REQUIRE_APPROVAL, WARN, ALLOW, NOT_APPLICABLE |
| REQUIRE_APPROVAL | 3 | WARN, ALLOW, NOT_APPLICABLE |
| WARN | 2 | ALLOW, NOT_APPLICABLE |
| ALLOW | 1 | NOT_APPLICABLE |
| NOT_APPLICABLE | 0 | Nothing |

## Specificity Rules

Specificity is a tie-break ONLY after strictness rank. Dimensions scored 0-5:

- **Scope specificity**: tool/action/sandbox-scoped > family-wide default
- **Family specificity**: explicit family assignment
- **Risk specificity**: explicit risk tier / ceiling
- **Tool specificity**: tool-scoped reason codes
- **Action specificity**: approval requirements, violations
- **Data specificity**: data residency reason codes
- **Sandbox specificity**: sandbox posture reason codes

Specific ALLOW must never override general DENY. Specific WARN must never override DENY.

## Resolver Integration

The resolver now attaches conflict metadata to every `ResolvedPolicySet`:

1. Existing `aggregate_family_decisions()` produces initial family decisions
2. New `_attach_conflict_metadata()` calls `resolve_policy_conflicts_strictest_wins()`
3. Resulting `conflict_resolution` (dict) and `conflict_hash` (str) are stored on the `ResolvedPolicySet`
4. If conflict algebra computation fails (defensive catch), metadata is silently omitted
5. Full backwards compatibility: conflict fields default to `None`

## Known Limitations

1. Conflict classification is a conservative first version using existing reason_codes, family names, and metadata. Future versions may add deeper semantic analysis.
2. `_check_metadata_conflicts()` uses pattern matching on reason_code prefixes (RISK_, TOOL_, DATA_, etc.) — these are aligned with existing adapter conventions.
3. Resolver integration uses a defensive try/except on conflict computation. If conflict algebra fails (should never happen in practice), metadata is silently omitted rather than crashing the resolver.
4. Empty `family_decisions` produces `NOT_APPLICABLE` with `NO_APPLICABLE_POLICY` — this is by design, not a bug.

## Deliberately Not Implemented

- **No enforcement**: Conflict outcomes are purely observational metadata
- **No runtime bridge**: No integration with `AgenticRuntime.submit()` enforcement
- **No approval activation**: Conflict resolution does not trigger approval workflows
- **No command blocking**: Stricter conflicts do not block commands
- **No sandbox reconfiguration**: Sandbox policy card conflicts do not change sandbox behavior
- **No multi-round resolution**: Single-pass strictest-wins only; no iterative negotiation
- **No external conflict feeds**: No database, file discovery, or external conflict data sources
