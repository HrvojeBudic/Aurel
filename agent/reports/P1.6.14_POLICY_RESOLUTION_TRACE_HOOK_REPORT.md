# P1.6.14 — Policy Resolution Trace Hook Report

**Status:** ACTIVE
**Date:** 2026-06-24
**Phase:** P1.6 — Policy Cards & Behavioral Contracts
**Predecessor:** P1.6.13 — Policy Conflict Algebra & Strictest-Wins Rules
**Successor:** P1.6.15 — Policy Violation Trace Hook

## Purpose

P1.6.14 creates trace-compatible policy resolution evidence; it does not write to the Ledger, enforce policy decisions, activate approvals, block commands, or change runtime sandbox behavior.

## Why Policy Resolution Trace Hook Exists

Custos shadow decisions produce rich metadata (resolution hashes, conflict classifications, effective actions, source card/family identifiers) that should be traceable and verifiable. P1.6.14 wraps this metadata into a deterministic, hash-ready trace-compatible evidence envelope without coupling to the real Ledger or runtime enforcement machinery.

## Relationship to P1.6.12 Runtime Projection

P1.6.12 attaches `PolicyShadowProjection` to `ObservationEnvelope.artifacts`. P1.6.14 adds `resolution_trace_id` and `resolution_trace_hash` to the projection so the trace envelope can be cross-referenced from runtime observations.

## Relationship to P1.6.13 Conflict Algebra

The trace envelope includes `conflict_hash` and `conflict_codes` from P1.6.13 conflict algebra. If conflict metadata is missing, the trace event degrades gracefully with empty `conflict_hash` and empty `conflict_codes`.

## Hash and Canonicalization Strategy

- `policy_trace_canonical_dict(event, include_hash=False)` → deterministic dict with sorted lists
- `policy_trace_hash(event)` → SHA-256 over `json.dumps(canonical_dict, sort_keys=True, separators=(",", ":"))`
- `trace_id` = `trace_hash` (deterministic, no external randomness)
- `trace_hash` is excluded from the hashed representation (same pattern as all Custos hashes)
- Shuffled `source_family_ids`, `source_card_ids`, `reason_codes`, `conflict_codes` produce identical hashes

## Resolver Integration

1. Existing `aggregate_family_decisions()` produces `ResolvedPolicySet`
2. `_attach_conflict_metadata()` adds P1.6.13 conflict data
3. `_attach_trace_metadata()` builds trace event from resolution + conflict metadata
4. `resolution_trace`, `resolution_trace_hash`, `resolution_trace_id` stored on `ResolvedPolicySet`
5. `with_canonical_hash()` called last (trace metadata excluded from `canonical_hash`)

## Runtime Projection Metadata Integration

`project_policy_resolution_against_runtime()` now extracts `resolution_trace_id` and `resolution_trace_hash` from the `ResolvedPolicySet` and stores them on the `PolicyShadowProjection`. These fields appear in the canonical projection dict.

## Shadow-Only Guarantee

- `shadow_only=True` is enforced by `PolicyResolutionTraceEvent.__post_init__()`
- `enforced=False` is enforced by `PolicyResolutionTraceEvent.__post_init__()`
- No `AgenticRuntime` import, no `AurelTraceLog` write, no runtime.py changes
- All trace objects have no `enforce`, `block`, `apply`, `approve`, `submit`, `write_ledger` methods

## Why This Is Not Full AurelTrace / Ledger

- No `AurelTraceLog` write or append
- No `TraceEvent` creation
- No `trace.py` import
- No real Ledger integration
- P1.6.14 produces self-contained evidence objects that are future Ledger-compatible but not Ledger-integrated

## Known Limitations

1. No `AurelTraceLog` integration — trace events exist only as metadata on `ResolvedPolicySet`
2. No `ObservationEnvelope.artifacts` integration — trace hook is resolver-only, not submit-level
3. `projection_hash` and `runtime_snapshot_hash` are empty strings in resolver-only context (populated only when projection is computed)
4. `trace_id` is the hash itself, not a separate UUID — deterministic but not human-readable

## Deliberately Not Implemented

- No Ledger write
- No trace.py integration
- No AurelTraceLog append
- No ObservationEnvelope.artifacts integration
- No runtime.py changes
- No AgenticRuntime.submit() changes
- No enforcement, approval, sandbox, or command blocking
- No fail-closed apply
- No Output Passport
- No Golden Thread B
